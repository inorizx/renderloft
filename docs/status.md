# RenderLoft 当前状态

这是一份会随项目变化而更新的状态摘要。具体行为以代码和测试为准。

## 已完成

- **一个批次可以自动铺到多条连接上（账号池的第一步）**（2026-10-26）：调用方**不再需要选账号**——
  提交时不指定 `connectionId`、而配方的 `allowedConnectionIds` 列了多条连接，run 就按序号轮转
  落到这些连接上（`RecipeBinding::connection_for_run`）。只列一条的配方行为逐字节不变；
  显式指定连接仍走原来的 scope 校验。判据：`a_batch_spreads_over_the_recipes_connection_pool`
  （4 条 run → 连接 revision 1,2,1,2）。
  ⚠️ 这一版是**均匀轮转**，不是按容量加权：创建时不知道各账号此刻有几个空位（那要问平台）。
  3+1 的池子上 4 条会先分成 2/2，多等一轮；按容量派单 + "未尝试过的 run 可改派"是下一步。
  ⚠️ 已知缺口：池里某个成员被删除 / 停用时，这批会整体 `CONNECTION_NOT_FOUND`；
  成员过滤与熔断（401 / 余额不足 / 连续被拒）还没做。
- **调度按平台声明的并发容量跑，不再恒为 1**（2026-10-26）：`available_slots()` 的静态值只是
  兜底，真正的容量来自连接上的 `/openapi/v2/queue/status`——`concurrentLimit` 是**用户买到的**
  并发位（实测本机账号是 3，不是 1），`runningCount` 是平台侧占用（**含网页控制台、别的工具
  提交的任务**）。每轮可领 = `limit − max(平台占用, 本地在跑)`；容量缓存 30 秒（2 秒一轮不能
  每轮都问平台），**被平台拒一次就停手本轮并丢掉缓存**——否则 tick 会把队列里的 run 全领出来
  挨个撞，三条 run 一起进退避。查询失败退回静态 1：接口挂了只慢不死。
  判据：`scheduler` 4 条新用例（一轮领满 3 条 / 平台占用优先 / 拒一次即停手 + 缓存失效 /
  缓存只查一次）+ `runninghub` 2 条（官方字段形状与脏值、`TASK_QUEUE_MAXED` 与其它拒绝分得开）。
  负对照：把容量查询改成恒 `None` ⇒ 第一轮只领 1 条，`uses_the_platform_declared_capacity` 变红。
- V2 本地 Rust Daemon、SQLite 工作区和 `/api/v1` HTTP/SSE 接口。
- Recipe / Connection / Operation / Run / Attempt / Asset / Artifact 核心模型。
- 持久化调度、Provider 提交、远端对账、取消、重试和结果归档。
- RunningHub 国内 / 国际连接、API Key 凭据存储、应用链接或 ID 导入、参数读取、媒体上传、任务查询和结果下载。
- 稳定架构和技术边界见根目录 [`ARCHITECTURE.md`](../ARCHITECTURE.md)。
- ComfyUI 本地或远程 API 工作流执行。

  几个，运行表单的 `model` 字段据此变成下拉；连接级 `defaultModel` 在运行与配方都没点名时兜底。

  ——引用的是**绑定**不是密钥，所以密钥不出凭据库、那边轮换自动生效、被引用的连接删掉/停用会立刻报错。

  徽章；密钥本体永不出凭据库。

  覆盖表单校验提示、原生确认框、无障碍标签与空态文案；语言在「服务配置」中切换，未选择时按系统语言确定。

  目录名刻意**避开安装目录**（NSIS 默认装到 `%LOCALAPPDATA%\RenderLoft`，同名会让程序文件与用户数据
  混在一个文件夹里，实测过）。
- 发布链路：版本号收敛为**单一真相来源**（根 `package.json`，其余 5 处由 `scripts/version.mjs` 同步，
  `pnpm verify` 与 CI 都校验一致）；`v*` tag 触发 `.github/workflows/release.yml` 打包并发布
  GitHub Release（安装包 + 免安装 zip + Linux 便携包 tar.gz + `SHA256SUMS.txt`），发布前校验 tag 与版本号一致。
- 命令行可用性：安装包会把安装目录加进**用户 PATH**（`desktop/nsis/hooks.nsh`，卸载时摘除；
  逻辑有 30 条断言的独立测试 `scripts/test-nsis-path-hook.mjs`）；CLI 失败时信封走 stderr、
  退出码 1，成功走 stdout、退出码 0 —— 所以任务计划里 `if ($LASTEXITCODE -ne 0)` 是有效的。
- 客户端自愈：CLI 与 MCP 发现 daemon 没在跑时会自己把旁边的 `renderloft.exe` 拉起来并等它健康
  （**只启动，不拥有**：不代管其生死、不改环境变量、输出落 `daemon.log`），连接失败时把
  "自动启动也失败"的原因一并报出；`tools/list` 仍是本地常量，daemon 不在也能先看见工具。
- 完成回调（webhook）：`operation run --callback-url` / MCP 的 `callbackUrl`。任务进终态时
  daemon POST 一份终态快照（`operationId` / `status` / `runs`）到该地址，失败按退避重试并留投递记录。
  触发方式是**后台按状态补扫**（不是在各终态出口各挂一处）：于是 reconcile / scheduler / cancel /
  hygiene 哪条路把任务推到终态都覆盖，**daemon 当时没在跑、重启后也会补上**（24 小时窗口内），
  且幂等（已有投递记录就不再补）。
  地址规则是 **https，或回环地址的 http**（`127.0.0.1` / `localhost` / `[::1]`；内网与公网只收 https）。
  可配 **HMAC-SHA256 签名**（头 `X-RenderLoft-Signature: t=…,v1=…`，被签名的是 `"{t}.{请求体原始字节}"`），
  接收端据此验证来源并防重放；密钥存系统凭据库、**只进不出**，写入只有 CLI 一条路
  （`callback set-secret` / `status` / `clear-secret`，MCP 无对应工具）——没配密钥时不带签名头。
- 后台循环的日志改为"写失败就算了"：此前 stdout/stderr 一旦断开（管道关闭、日志文件被删等），
  循环每轮的日志写入会 panic 并把该循环静默带走——症状是任务提交成功却永远停在 `ACCEPTED`，
  看起来像平台卡住。启动期日志仍保持"写不出去就大声失败"。
- Linux 无头交付：CLI / 网页控制台 / MCP 三入口共用同一个 daemon；`pnpm build:linux` 产出
  `RenderLoft_<版本>_x64-linux.tar.gz`（三件套 + `dist/`，解压即用），CI 的 `linux-portable`
  job 从**解压出来的包**做全链路冒烟（CLI → daemon → 控制台 → MCP），防打包静默烂掉。
  Linux 不做桌面壳；密钥走系统密钥环（Secret Service）。
- 媒体资产按**字段键**定位（根因修复）：资产的语义身份是 `(recipe revision, 字段键)`（如 `475::image`），
  数组位置只是 HTTP 兼容编码。新导入/新追加的 revision 一律写 keyed `mediaMapping`；旧 revision 经同一
  归一化路径继续可读；keyed revision 收到位置数组明确拒绝（`POSITIONAL_ASSETS_UNSUPPORTED`）。
  Provider（RunningHub / ComfyUI）按字段键写入节点槽位，不再按下标或扫描工作流猜目标；
  未知字段键/资产缺失/checksum 不符在提交前报稳定错误码（避免 scheduler 读到空字节把空文件发上去）。
  媒体提交闭环补齐：CLI `operation run --asset '字段键=文件'`（自动上传）与 `--dry-run`（只读预检，
  与提交共用判据、不落库不花钱）、MCP 的 `assets`（keyed 对象）与 `dryRun`（runs[] 里的 assets 此前会被
  静默丢弃）；GUI 解除「必须连续填文件槽位」的提交限制。Agent 实操见 [`agent-cookbook.md`](agent-cookbook.md)。

- **迁移与备份**：工作区本身就是普通文件（`%LOCALAPPDATA%\renderloft-workspace` 的库 + `artifacts\`），
  换机器＝拷目录、恢复＝换回去；README 的「你的东西在哪」写明了路径与"密钥必须由人重填"。
  只读动词 `workspace backup`（CLI `workspace backup --to <目录>`、MCP `renderloft_backup_workspace`）
  用 `VACUUM INTO` 导出一份**一致**的快照并整份拷 `artifacts\`——因为运行中的 WAL 库直接拷会缺数据
  甚至打不开，而且**不报错**。恢复**没有**对应动词（`daemon stop` → 换目录 → 任意 CLI 命令把 daemon
  拉起来）。验收判据（备份出来的库能重新打开、数据与源一致）有**真库**测试钉住；四道校验各有负对照
  （停用守卫后那四条测试实测变红）。界面上还没做按钮（CLI / MCP 已可用）。

- **任务卡住时「为什么没在动」**：每个"在等什么"的非终态 run 都给出稳定原因码 + 一句人话 +
  死线 + 到点会怎样 + 现在能做什么（`operation get` 的 operation 级与每个 run 上都有）。
  摘要列表（`operation list`）也带同一判据的**精简版**（只有原因码与死线，人话与 nextActions
  留在 `get`）—— 因为调用方是**先 list 再 get** 的：只有 `get` 有，等于逼它为列表里每一条各打
  一次 `get` 才知道该看哪一个。原因码与严重度（不确定 > 退避 > 提交中 > 排队）**只有一张表**
  （`domain::operation::ATTENTION_LADDER`）：`get` 的挑选与 `list` 摘要那条相关子查询的
  `IN` / `ORDER BY CASE` 都由它生成，不手抄（一条相关子查询，不是 N+1）。
- **`operation retry` 进 CLI / MCP**：`renderloft-cli operation retry --operation <id> [--run <id>]`
  / MCP `renderloft_retry_operation`。此前它**只有 HTTP**（界面点得到，CLI / MCP 够不着），
  而 `attention` 的 `nextActions` 早就把 `operation.retry` 写成"下一步能做什么"——名字够不到就是
  死路（有守卫钉住"`nextActions` 点到的名字必须是表里真实存在的动词"）。它是**新建一个 operation**
  （复用原 run 的配方修订、inputs 与 assets；`clientRunId` 带 `-retry-<时间戳>`、新 idempotencyKey），
  所以**返回的是新 operationId，要改盯新的那个**，且每个重试的 run 都会**再计费一次**；
  `--run` 只重试一条 —— 批量里只失败了几条时用它，重跑整个任务会把已成功的那几条也再提交一次
- **界面上也看得见「它其实没在动」**：任务卡片直接写一行
  「它其实没在动 · 等确认 · 15:52 判失败」（没有死线的档位**只写原因**，不说"到点判失败"），
  详情弹窗里再给一句解释（在等什么、到点会怎样），批量里具体哪条 run 在等也有角标。
  文案由界面**按原因码**取自己的 i18n（中英各一份），**不显示后端那句中文原文**——否则英文界面里
  会蹦出中文；原因码才是机器契约。另外「重新运行」现在会**先问一句**：它是新建任务、会再计费一次。
  （也就是再花一次钱）。
- **提交结果不明时，「字节到底出没出去」有证据了**：此前 run 落 `SUBMISSION_UNCERTAIN` 时那次
  attempt 的 `remote_handle_json` 与 `error_json` **都是空的**，事件里只有一句不含原因链的话，
  日志那一行要等到死线才写 ⇒「连接被拒」（字节一定没出去）与「发出去后超时」（可能已经在平台上
  跑起来了）在库里长得一模一样。现在网络失败的结构化错误会**存到那次 attempt 上**，并带一个
  判据 `nothingSent`：只有**连接被拒 / DNS 解析失败 / 握手阶段超时**才为 `true`
  （证据码写在 `nothingSentEvidence`），其余（发送后超时、连接被重置…）一律 `false`。
  ⚠️ 它**不是"可以重投"的许可**：模糊类（`false`）要能安全重投，需要**平台侧去重**，而幂等指纹
  从来没发给平台（`RecoveryProof` 在生产代码里没有生产者）——所以那一类**绝不自动重投**
  （哪一类会自己重试，见下一条）。判据与查法见 [`agent-cookbook.md`](agent-cookbook.md) §11d。
- **证明得了「字节没出去」的提交失败会自己重试**：连接被拒 / DNS 解析失败 / 握手阶段超时这三类，
  平台**什么都没收到**（重投不可能重复扣费），所以不再落「等确认」空转到死线（默认 1 小时），
  而是走**已有的**退避重试（`RETRY_BACKOFF`，30 秒后自动重试，与平台拒绝/限流/5xx 同一档语义）。
  证明不了的那一类（发送后超时、连接被重置）**照旧等死线、绝不自动重投**——那才是"可能已经收下"。
  判据只有一处（`submission_is_unknown`）：**落状态与 tick 的计数同源**（写这条时实测抓到过一处
  分歧：只改落状态那处，run 进了 `RETRY_BACKOFF` 而计数仍报 uncertain）。
- **「结果」视角：产物自己的入口**（2026-10-18）：愿景把"**结果**"和连接 / 应用 / 任务并列为四个产品
  名词，而在此之前产物**只能顺着任务找到** —— 要先想起是哪次跑的，才能看到那张图。
  现在侧栏多一个「结果」：一屏缩略图、**最新在前**、点开就是现成的预览框（左右翻 + 下载），
  每条还能显示**已知**的来源（`应用名 · 那条 run 的标签`，复用了上一批的 `runGroupLabel`）。
  三处刻意的取舍：① **来源只在已知时显示** —— 产物列表本身不带"哪个应用"（那要按 run 反查），
  所以只用工作区**已经缓存**的任务来解析，不为每张产物再发一次请求；解析不到就**什么都不说**，
  不编一个来源；② **不做筛选**：服务端没有按类型/应用筛的接口，而在**一页**上做客户端筛选是假的
  （用户以为筛的是全部）；③ **不做删除**：产物删除只随任务级联（`delete_operations`），
  单独删产物要新端点，而那是个破坏性动作，得单独想清楚。
  为此给产物列表加了**第二个方向**：`order=desc` + `before <id>`（"比它更旧的，最新在前"）。
  为什么必须由服务端给：默认方向是**升序**，第一页是**最旧**的一批 —— 「结果」视角用它根本拿不到
  最近的产物，除非把整个列表翻完再倒序（拿流量换顺序）。两个方向混着传报 `CURSOR_CONFLICT`，
  不默默挑一个（挑错了会给出"看起来对、其实是最旧的一批"的结果，而调用方不会发现）。
  ⚠️ **部署时又抓到一条**（同一个功能的第三层）：CLI/MCP 那侧**静默忽略了方向** ——
  动词表里加了 `order` / `before`（所以 CLI 认得旗标），但客户端的查询串是**手写拼接**的，
  与表**没有编译期联系**，漏了转发 ⇒ `artifact list --order desc` 有数据、格式也对，
  看起来"能用"，其实返回的是**最旧**的一批。修好后加了
  `artifact_list_forwards_the_direction_flags`（端到端那条链的**中间一段**，服务端那半已有契约测试）。
  教训：**"界面能用"不等于"CLI/MCP 能用"** —— 三个入口共用一条执行能力，但**接线是三处**。
  ⚠️ 这里有一条**测试教训**：HTTP 那条契约测试跑的是**替身**，它碰不到那条 SQL ——
  实测把 sqlite 的 `ORDER BY id DESC` 改成 `ASC`，HTTP 那条**照样绿**。所以判据另落在
  sqlite 侧的 `artifact_list_pages_in_both_directions` 上，两条各有各的负对照。
- **表单草稿活过重启**（2026-10-18）：产品愿景那句"**保存参数**、复用历史"的前半句。
  此前表单的值只活在**内存**里（`runnerSessions` 按标签存，切走再回来还在，**关掉就没了**），
  于是一张填了一半的长表（多提示词、多商品图那种）关掉应用就白填。
  现在每个应用的草稿落在 **localStorage**（`renderloft-runner-drafts`，带**版本号**：形状变了就
  整份丢弃而不是猜着迁移 —— 草稿是"用户随手填的东西"，**猜错的迁移比丢掉更糟**，它会填进错的
  参数，而那是花钱的）。四条边界都属于"符合直觉"那一类：
  ① **活过重启**（本次要的就是它）；② **关标签页 = 清掉**（那是"这个应用我不用了"的显式动作，
  与浏览器里关掉一个填了一半的页面同义）；③ 表单上给一个「**清空表单**」出口（只在真有内容时
  出现）——否则用户只能一个格子一个格子地删；④ **标签列表不持久化**：草稿与"开了哪些标签"分开存，
  把标签也存下来会让重开界面后**多出几个没开过的标签**（今天重开就是干净的一排），那不是用户要的。
  两个刻意的技术决定：**行草稿只存 `id`/`values`/`files`** —— 不存 `status`（那是**上一次会话**的
  执行状态，存下来会让重开表单显示一个假的"运行中"），也不存 `clientRunId`（它**参与幂等**，
  带回来最坏是服务端去重、"点了生成却什么都没发生"）；落盘**节流 400ms** 并在
  `pagehide`/`visibilitychange` 时立刻兑现（"刚敲完就关掉"是最常见的一种关法）。
- **「用这套参数再跑一次（可改）」**（2026-10-18）：产品愿景的渐进式路径第二级是"**保存参数、复用历史**"。
  此前唯一的复用路径是任务列表里的「重新运行」—— 那是**立刻再提交一次、参数不能改**；想改一个参数
  重跑，只能把整套参数重新打一遍。
  现在任务详情与批次详情里**每条 run** 都有一个入口：打开那个应用的表单、把这次提交的参数**预填**好，
  改不改、跑不跑由人按 —— **钱永远由人按**（它与「重新运行」刻意是两个入口，不是一个开关）。
  三处取舍：① 只填**当前 schema 认得**的字段（应用重新导入过之后，旧修订留下的键没有意义）；
  ② 素材**按字段键**还原，旧的位置编码（`fieldKey` 为空）**跳过**——不许猜字段键，猜错就是把钱花在
  错素材上（实测：跳过后文件位是空的、必填标记在、点「开始生成」**一个请求都不发**）；
  ③ 那个应用的表单里已有内容时先问一句，**不静默丢掉**用户打了一半的东西。
  为此详情接口补了两个字段：每条 run 的 `recipeId`（界面靠它跳到 `/library/:recipeId`；查不到就
  **不给那个入口**，宁可不给也不要跳到一个 schema 都不一样的表单里）与 `assets`（形状与
  `POST /operations/validate` 的解析结果一致）。`recipeId` 按不同修订缓存查询：正常一批查 1 次。
- **5xx 判成「提交结果不明」**（2026-10-18，**一个钱的取舍，已定**）：`map_http_error` 把 429 与 5xx
  都标成"可重试" ⇒ 5xx 会走退避重试（**盲投**）。可 500 可能是**网关 / 内部错误发生在受理之后**
  ⇒ 平台**可能已经收下**并照常计费，盲投就是"平台上可能有两个任务、扣两次钱"。
  按铁律二它和"发出去之后超时"同类，所以现在：**提交路径**上的 5xx 由
  `safety::map_submit_http_error` 标成"结果不明"（`details.submissionUnknown`），
  于是 run 落 `SUBMISSION_UNCERTAIN`、**不自动重投**；**4xx（尤其 429）不受影响**（明确拒绝
  ⇒ 一个字节的活都没接 ⇒ 重试不可能重复计费）。
  **代价说清楚**：RunningHub **没有任何接口**能回查"我那条任务在不在"，所以那边遇到 5xx 会等到
  死线（默认 1 小时）再人工决定。换来的是**永远不会悄悄扣两次**。
  ComfyUI 不一样：编号是我们自己定的，所以 5xx 与"响应丢了"**同一条处理**——报"不确定 + 可按 id
  回查"，通常几秒就查清（这条判据与网络那条共用一个函数，免得两处各写一份）。
  只改**提交路径**：查询 / 取消 / 队列快照收到 5xx 只是"这次请求失败"，继续用 `map_http_error`
  —— 否则会把一次查询失败升级成"可能已经收下"，那是另一种谎。
  顺带修一处：`SUBMISSION_UNCERTAIN` 的 run 此前**不落 `error`**（只写进 attempt），
  于是调用方在 run 级看到 `error: null`——而它正处在"要不要再花一次钱"的判断里，最需要知道
  **为什么不确定**（连接断了？还是平台 500？后者意味着可能已经收下）。cookbook §11 那句
  "读 run 的 `inputs` 与 `error` 一起读"也依赖这一列真的非空。
- **详情接口补上每条 run 的 `inputs`**（2026-10-18，**修的是一句说了没做的事**）：`run_response`
  此前**从来没发过** `inputs`，而服务出去的文案早就承诺了它 —— `renderloft_get_operation` 的描述写着
  "每条 run 都带提交时的 `inputs`"，cookbook §11 的恢复建议也建立在它之上（**读 `inputs` 与 `error`
  一起读、改对了再重投**）。调用方照文案去做会**找不到** `inputs`，而它正处在"要不要再花一次钱"的
  判断里：要么猜、要么盲投 —— 盲投正是铁律二要防的事。
  怎么发现的：给预览框做"结果按输入分组"时，界面拿不到 `inputs`；我一开始还照着那句文案
  在 TS 里写下"后端一直在发，只是没声明"（**那句话是错的**，是照文案想当然）。回头查端点才查出根因。
  现在详情与 `GET /api/v1/runs/{id}` 都带 `inputs`（与提交时那份逐字相等，有契约测试钉着）；
  **列表接口仍然只回摘要**（`runCount` + `attention`），那条边界没动，也有反向断言。
- **结果按输入分组查看（界面）**（2026-10-18）：这是愿景里"批量是核心能力"那五条里的另一条。
  实情是**分组一直都在**——产物本来就按 run 取（`listArtifacts(runId)`）、摊进预览框的顺序也已经是
  run 顺序——缺的只是**标签**：每一项贴的都是任务名，于是"12 张图里哪 3 张来自第 2 条提示词"
  没法回答。现在预览框（任务中心 + 任务页两处，共用 `shared/lib/runLabel.ts` 一份判据）的标题
  是 `任务名 · <这条 run 的标签>`，左右翻就能看出每张出自哪条输入。
  标签判据三级：① 调用方**自己给的** `clientRunId`（认得出后端自动生成的 `run-<32 位十六进制>`，
  那种一个字的输入信息都没有）；② 输入里最像提示词/描述的字符串摘要（复用 `fieldHeuristics` 的
  `LONG_TEXT_HINTS`，不另写一份启发式）；③ `run#<序号>` —— 只剩位置信息时就如实说位置，**不编标签**。
  顺带把 `RunRef.inputs` 声明上（后端一直在发，前端只是没声明）。
- **批量里可以只重试失败的那几条（界面）**（2026-10-18）：此前界面只有「重新运行**整批**」——
  一个 10 条里失败 2 条的批量，用户要么把已成功的 8 条也再提交、再计费一遍，要么什么都不做。
  而"**失败项单独重试**"是产品愿景里明确列出的批量核心能力，后端（`.../runs/{runId}/retry`）与
  CLI/MCP（`operation retry --run`）**早就有**，只有界面没接（API 客户端里的 `retryRun` 当时是
  **零引用**）。现在批次详情里有「只重试失败的 N 条」：逐条建新任务、确认框写明"再计费 N 次"，
  且**取消的不算**（那是人主动停的）。界面**不自己拼多 run 的提交**：它拿不到 run 的
  inputs/assets，拼错就是把钱花在错参数上——让后端用它自己存的那份。
- **退避重试也有终点**（2026-10-18）：此前 `RETRY_WAIT` **没有死线也没有次数上限** —— 平台一直拒
  就每 30 秒重试一次、**永远不结束**：用户看到的是一个永远「进行中」的任务，而 `attention` 那时
  只能说"正在退避重试"（说"到点判失败"是假话，所以上一批把那半句删掉了）。
  现在它用**连接上早就存在的那个旋钮**（`trackingDeadlineSeconds`，默认 1 小时）：
  第一次进这一档时写下死线，之后每次重试**沿用同一个**（不是每失败一次往后推一小时，那等于没有死线），
  到期后在下一次重试本该发出去的那一刻**判失败**（`RETRY_EXHAUSTED`，不提交、不 prepare）。
  判在这一刻而不是另起清扫，有三个好处：不需要新查询/新循环；daemon 当时没在跑也**不会漏**
  （开机后第一次 tick 就会认领并判掉）；时机与语义重合（**最后一次机会用完了**）。
  `attention` 的 `RETRY_BACKOFF` 那半句"到点判失败"因此又变回真话 —— 而且现在
  **"有死线才许说「到点会怎样」"是每一档都成立的不变量**（两种取值都有测试）。
  顺带修掉一处替身与真实现的偏差：假替身认领时会把 run **整个重建**（`tracking_deadline: None`），
  于是"看死线"的判据在测试里**永远看不到死线**（生产会判、测试说没判）—— 负对照实测过。
- **MCP 工具面压平：每个动词一个原生工具**（2026-10-18，一次架构决定）：此前是"元层"——
  两个工具（`renderloft_catalog` 索引 + `renderloft_call` 调用口），逐动作的只读/破坏性/花钱
  标注**只在 `catalog(<verb>)` 的返回里**。而审批层读的是 `tools/list` 里**每个动作那一格**
  `annotations`，一个工具只有一格、装 N 个动作时只能报最保守值 ⇒ 压平前"只读的"和"会花钱、
  不可逆的"在审批层**长得一模一样**。现在 16 个动词各一个工具（`renderloft_run_recipe` 这套名字），
  标注与表逐条相等、成本标记在描述首行；跨动词的流程/付费/长任务/失败重试搬进 `instructions`
  （只付一次，16 条描述里 `renderloft_` 出现 0 次）。
  `renderloft_catalog` **保留但降级为按需查阅的参考工具**（索引不再嵌在常驻描述里）；
  `renderloft_call` **从清单里撤掉、但仍然认得**（弃用窗口）。
  ⚠️ **代价是实测的，不是估算的**：常驻 1 135 → **3 035** token（0.89% → 2.37%），
  按需索引 4 572 → 3 197。设计文档原先写的"≤8000 字符"预算也被实测推翻（真实 12 534），
  上限按实测定在 13 200 并写进测试（失败时会打印"描述 / schema / 其余"三块各占多少）。
  验收：设计文档 §8-① 的五个问题**都能只读 `tools/list` ＋ `instructions` 答出来**（已实测）；
  §8-② 的交叉测试**没跑**（要真挂一个通用 agent ＋ 一次真实计费的任务，只能由人跑）。
- **取消时如实说"远端可能还在跑"**：`operation cancel` 的 `remoteMayContinue` 现在**也包含
  没有远端句柄的 run**（`SUBMISSION_UNCERTAIN` / `SUBMITTING` —— 句柄只有拿到平台回执时才有，
  所以恰恰是这两档没有）。此前它们只进 `cancelled`，用户会读成"平台上一定没有残留"，
  而平台上那一份可能正在跑并照常计费。还没提交的 `QUEUED` 仍然只进 `cancelled`。
- **ComfyUI 的「提交响应丢了」现在能查回来**（2026-10-18）：提交时**我们自己定 job id**
  （`prompt_id`，规范小写 UUID，从指纹派生）+ 一个唯一的 `client_id`，ComfyUI 原样采用并回显
  ⇒ 响应丢了也知道该查哪个 id。于是那种失败不再"等死线判失败"，而是报
  `Uncertain + 可按 id 回查`：run 拿到**远端句柄**、进对账队列，`GET /history/{prompt_id}`
  查得到就正常收尾（通常几秒）。这是 `RecoveryProof::LookupByRequestId` 在**生产代码里的
  第一个生产者**（此前只有测试在造 `SubmitOutcome::Uncertain`，scheduler 里那条分支不可达）。
  ⚠️ 两个坑都钉在代码注释里：① `/history` **只在任务执行完才写**（排队/运行中在 `/queue`），
  只看 history 会把"平台正在跑"读成"平台没收到"——所以对账要先问一次队列；② `prompt_id` 形状
  不合规时服务端直接 400，所以生成的是真 UUID 形状（有测试钉住）。
  另外**「能不能证明字节没出去」这条判据收敛到领域层**（`SafeError::submission_is_unknown`）：
  调度器与驱动都必须给出同一个答案（此前各写一份，实测踩到过分歧）。
- **等待确认的 run 不再占住连接唯一的执行位**：一个 `SUBMISSION_UNCERTAIN` 的 run 此前会占满
  这条连接唯一的执行位（默认并发 1）**直到死线（默认 1 小时）**，后面的 run 全排队 —— 而平台上
  可能一个都没在跑。现在占位只算 `ACCEPTED` / `RUNNING`（真的在平台上跑的）；撞上平台上限时
  平台会拒，而 RunningHub 的拒绝（`TASK_QUEUE_MAXED`，实测"拒了一分钱没花"）本来就是可重试的
  ⇒ 退避 30 秒自动重试。对账队列（`list_active_runs`）**照旧**包含不确定的 run，否则它永远不会
  被确认。
- **产物字节取一次就留在本地**（2026-10-26）：RunningHub 只给 URL 不给字节，于是此前
  **每看一次图就回源下一次** —— 「结果」页一屏几十张缩略图就是几十次下载，重启后再来一遍；
  而本地缓存目录一直都在，只是**从来没有人往里写**。
  现在 `/artifacts/{id}/bytes` 与「另存到下载目录」共用同一条取字节的路：**本地缓存优先**，
  回源命中后就地落盘（`artifacts\<id>`），第二次直接命中；`byteSize` 也从 0 刷成真实大小
  （0 的含义因此从"字节在平台上"变成"还没取过"，README 与 cookbook 两处说法已同步）。
  响应带 `ETag`（有 checksum 用它，没有用 `artifact-<id>`）+ `Cache-Control: private,
  max-age=31536000, immutable` + `Vary: Authorization`，`If-None-Match` 命中回 **304** ——
  WebView 反复画同一张缩略图时连本地传输都省了。
  顺带补掉一处**只增不减**：`delete_operations`（界面删任务与 30 天清扫）现在把对应产物的
  缓存文件也删掉 —— 此前只删库里的行，`artifacts\` 里的图片永远留在磁盘上。
  判据三条，各自做过负对照（分别停用"本地优先"、"落盘"、"删文件"，实测都会变红）：
  `artifact_bytes_are_downloaded_once_and_cached`（数回源次数）、
  `cached_artifact_bytes_land_on_disk_and_refresh_the_real_size`、
  `deleting_an_operation_removes_its_cached_artifact_files`。
  刻意**不做**缩略图生成：那要给 daemon 加图像解码依赖（编译与内存都变重），而字节已经
  在本地了，渲染一张 PNG 的瓶颈不在传输。
- **Windows 的系统代理现在真的会生效**（2026-10-26）：reqwest 只认 `HTTP(S)_PROXY`，
  **不读** Windows「Internet 选项」里的系统代理 —— 而 Clash / v2rayN 默认只改注册表、
  不改环境变量。实测（本机，2026-10-26）：`ProxyEnable=1 / ProxyServer=127.0.0.1:7897`、
  环境变量全空；直连 `google.com` 超时、走代理 302 ⇒ 在"平台必须经代理才到得了"的机器上，
  RenderLoft **根本够不着**，而界面只会说"连接测试失败"。
  现在 `v2/outbound.rs` 只给**一份**方案（优先级：环境变量 > 系统代理 > 直连），
  **所有**出站客户端（四个 driver、产物拉取、完成回调）统一经
  `infrastructure/providers/proxy.rs::configure()` 装配 —— **只装一处、没有例外**，
  否则"提交走了代理、查询没走"会变成新的悬案。**每一次请求都重新解析**
  （`Proxy::custom` 的闭包），不是建客户端时算一次：系统代理是活的，用户很可能先开应用
  再开代理软件；浏览器改完设置下一次请求就跟上，我们也一样。
  **边界只有一句：只读不写。** 不提供 `RENDERLOFT_PROXY` 这类手工开关（这是第二份真话，
  迟早和系统设置打架），不改任何系统设置，读不到、读不懂就退回直连。
  三处刻意的取舍：① **只有回环是隐式直连**（`localhost` / `127.0.0.0/8` / `::1`），
  与 Chromium 一致（它的 `<-loopback>` 默认就是关的）；**私有网段不隐式绕过**——企业内网
  走代理是真实用法，绕过等于替用户否决它，内网 ComfyUI 由代理软件自己写进 `ProxyOverride`
  （Clash 写了 20 条）。② `ProxyOverride` 按 `*` 通配匹配，`*.example.com` 同时匹配裸域
  （人的直觉优先于 WinINET 的字面语义）；环境里的 `NO_PROXY` 也并进这张表（curl / git / npm
  都认它）。③ **socks 与 PAC 认得出但用不了**：不静默直连，错误括注会明说
  "系统代理 只给了 socks=…，用不了"——但也仅此一句，不占界面、不多开诊断字段。
  界面上**不为代理单开一行**（它是环境的事，不是设置页里能调的参数）；「运行参数」里
  不再报它，只有"复制诊断"那段文本带一句实际地址，供贴给别人排查。
  判据：`outbound.rs` 18 条纯逻辑用例（注册表两种写法、socks 记账与括注（系统/环境各一条）、
  `<local>`、通配/裸域、回环隐式直连与私有网段**不**隐式直连各一条、`NO_PROXY` 合并、
  **环境变量代理也必须豁免回环**、`ALL_PROXY` 覆盖全协议、三条优先级、空白值）+
  `proxy.rs` 3 条装配用例（假代理数请求行、回环必须直连、**开代理之后下一次请求就跟上**），
  外加一条 `#[ignore]` 的 live 用例（**直连必须失败、经代理必须成功**）。
  实测（2026-10-26 22:25，Clash 开系统代理、环境变量全清）：`✓ 直连失败、经系统代理成功
  （200 OK）`，日志为「系统代理 http://127.0.0.1:7897，绕过 20 条，含 `<local>`」——
  注册表这一路是真的把流量带出去了，不只是解析对。
  负对照：不装代理 ⇒ 假代理收不到请求；**去掉回环判定 ⇒ 回环流量打进假代理**（装配用例
  实测变红，2026-10-26）；把解析冻在建客户端那一刻 ⇒"后开的代理"那条红。
  ⚠️ **边界**：代理只影响**出站连接**；域名的本地解析与 SSRF 校验（`validate_resolved_url`）
  仍在本地做——所以"只有代理那头才解析得了"的域名会先在 `PROVIDER_URL_UNRESOLVABLE`
  被拦住，那是安全边界，不是这一版要放开的东西。

## 暂未实现或暂缓

- **模糊类（"可能已经收下"）的自动重投还没接**：能证明"字节没出去"的那一类已经会自己重试了；
  剩下的那一类要能**安全重投**需要**平台侧去重**，而幂等指纹从来没有发给平台。
  调研结论（2026-10-18，逐条带官方出处）：**只有 ComfyUI 有抓手**（见上一条，但它给的是"能回查"，
  不是"能安全重投"）；**RunningHub 明确做不到**（创建接口没有任何客户端标识字段、所有查询只认
  它自己发的 taskId、也没有"列最近任务"接口）；**OpenAI 图像 API 明确做不到**（无幂等键、响应无 id、
  无回查接口）；通用异步平台默认做不到。所以对这几家，模糊类仍然只能等死线（判据见
  [`agent-cookbook.md`](agent-cookbook.md) §11d）。
- A2A Transport 及其 conformance 测试；当前没有 A2A 路由、代码或测试。
- Prompt Assistant 的生成端点：**评估后不做**（2026-09-22）。参数层的"这个字段该填什么"已由提示词模板与官方示例变量覆盖
  （确定性、可复现），任务层的"给个目标自动完成"由外部 AI 通过 MCP 驱动（见 README 的「用 AI 驱动它」）；
  居中的"AI 帮忙润色单个字段"两边都不需要。
  现有的 profile CRUD 与模板管理继续保留（它们服务的是模板配置，不是生成）。
- RunningHub 应用市场的站内搜索、作者浏览和完整发现体验。
- 发布渠道：**GitHub 是发布渠道，Gitee 是代码镜像**。CI（`.github/workflows/ci.yml`，push 触发）
  与 Release（`.github/workflows/release.yml`，`v*` tag 触发）都在 GitHub 上跑；Release 产出
  NSIS 安装包 + 免安装 zip + Linux 便携包 tar.gz + `SHA256SUMS.txt`（Linux 构建失败会拦截发布）。
  Gitee 侧是 **GitHub → Gitee 的 Pull 镜像**：代码与 tag 自动同步，**别直接往 Gitee 推**；
  Gitee 发行版的附件仍由本机手动上传（Gitee 不跑 CI）。
